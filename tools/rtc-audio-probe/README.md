# Диагностика аудио-тракта десктоп-сборки

## Зачем это

В десктоп-версии OwnCord отключён микрофонный пайплайн, а вместе с ним и
AI-шумоподавление: в RTC уходит сырой микрофон. Причина — баг, при котором
собеседник слышал тишину. В коммите `v0.8.9` он объяснён так: «в Electron
Chromium `RTCRtpSender` кодирует трек, полученный из
`MediaStreamDestination`, как тишину».

На macOS с Electron 42 это утверждение **воспроизвести не удалось** —
звук проходит нормально. Значит одно из двух: либо проблема
платформенная (Windows/WASAPI против macOS/CoreAudio), либо она возникает
только когда источником служит микрофон, а не Web Audio вообще.

Зонд отвечает на этот вопрос замерами вместо предположений.

## Как это устроено

Внутри одного окна поднимается петля из двух `RTCPeerConnection`, в неё
подаётся звук, и на приёмной стороне измеряется реально принятый сигнал.

Ключевая деталь: замер идёт **`AnalyserNode`-ом на принятом треке**, а не
метрикой `inbound-rtp.audioLevel`. Последняя считается на пути
воспроизведения и равна нулю, если приёмный элемент приглушён, — звук при
этом может идти прекрасно. Легко поставить ложный диагноз «тишина»;
не исключено, что именно это и произошло изначально.

Сценарии:

| | Что проверяет |
|---|---|
| **A** | Осциллятор → `MediaStreamDestination`. Проверяет само утверждение про Electron, без микрофона |
| **B** | Сырой микрофонный трек. Контроль: так десктоп работает сейчас |
| **C** | Микрофон → Web Audio → `dest`, контекст 48 кГц. **Это путь шумодава** |
| **D** | То же, но частота контекста родная для железа. Если C падает, а D проходит — виноват форс 48 кГц |
| **E** | Микрофон без эхоподавления. AEC — известный источник странностей при заворачивании трека в Web Audio |

## Запуск на Windows

Нужен Node.js 20+. Проверить: `node -v`. Если нет — поставить с
[nodejs.org](https://nodejs.org/) (LTS).

```
git clone https://github.com/odemaru/owncord.git
cd owncord\tools\rtc-audio-probe
npm install
npm start
```

`npm install` скачает Electron, это около 100 МБ и пара минут.

Откроется окно. **Говори в микрофон, пока идут тесты** — секунд десять,
иначе замеры пройдут по тишине и результат будет бессмысленным. Windows
может спросить разрешение на микрофон, его надо дать.

По завершении рядом появится файл `rtc-probe-<дата>.txt`. Его содержимое
и нужно прислать — там всё: платформа, версии, ключи запуска и цифры по
каждому сценарию.

## Если базовый прогон показал FAIL

Значит баг воспроизвёлся, и можно сразу проверить кандидатов на починку.
Каждая команда — отдельный прогон с другими ключами Chromium:

```
npm run probe:no-oop-audio
```

Выносит аудио-сервис Chromium обратно в основной процесс. Первый
подозреваемый: в Electron он по умолчанию живёт отдельным процессом в
песочнице, и это известный источник ровно таких симптомов.

```
npm run probe:no-audio-sandbox
```

То же, но снимается только песочница, сам сервис остаётся отдельным.

```
npm run probe:autoplay
```

Снимает требование пользовательского жеста. Помогает, если `AudioContext`
остаётся в состоянии `suspended`.

```
npm run probe:all-fixes
```

Всё сразу. Если проходит только этот вариант — дальше разберёмся, какой
именно ключ решает.

Каждый прогон пишет свой файл с отчётом. Присылай все.

## Как читать результат

- **A: FAIL** — утверждение из `v0.8.9` верно для этой платформы, Web Audio
  в RTC не проходит в принципе. Лечится ключами Chromium.
- **A: PASS, C: FAIL** — дело не в Web Audio как таковом, а в микрофоне
  как источнике. Смотрим на D и E: они показывают, виноват ли форс 48 кГц
  или эхоподавление.
- **A, C: PASS** — бага здесь нет, и пайплайн в десктопе можно включать
  обратно. Тогда десктоп получит и шумодав, и глобальные хоткеи.
- **B: FAIL** — сломан сам стенд или микрофон не даёт сигнала (молчали в
  него). Остальные результаты в этом случае недостоверны.
